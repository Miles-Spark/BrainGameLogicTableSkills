# 脑洞关卡制作优化版

## 适用场景

当用户提出以下意图时启动本工作流：

- `制作脑洞关卡<id>`
- `制作关卡<id>`
- `制作关卡<id>,<id>,...`
- 明确要求检查、修复、转换或生成脑洞关卡逻辑

## 多关卡并发策略

多关卡任务按关卡 ID 拆分为独立子任务，每个关卡使用独立输入、独立输出、独立命令执行结果和独立报告。

并发控制规则：

1. Phase 1-3 可以并行处理，因为不依赖共享资源。
2. Phase 4（脚本转换）和 Phase 5（unicli 调用）涉及外部进程，建议串行执行，避免进程冲突。
3. 单个关卡任一 Phase 失败时，记录失败点并跳过该关卡后续 Phase，不影响其他关卡继续处理。
4. 所有关卡的最终报告汇总为一份，分别标注每个关卡的状态。

## Skill 根目录

本 Skill 所有相对路径均以 Skill 根目录为基准，即 SKILL.md 所在目录。执行脚本或读取 references 时，必须基于此根目录拼接完整路径，不依赖 agent 当前工作目录。

记法：`$SKILL_ROOT` = 本 Skill 根目录的绝对路径。

## 用户工作目录约定

默认用户工作目录中包含 `BrainGameLevel` 文件夹。

```text
BrainGameLevel/
├── <LevelId>.md              # 原始策划案（只读，不覆盖）
├── <LevelId>_fixed.md        # 修复版逻辑图（新建或另存）
└── <LevelId>_fixed_output.md # 转换后逻辑图（由脚本生成）
```

先基于当前工作目录搜索 `BrainGameLevel` 目录。找不到时停止当前关卡并报告缺失目录。

## 工作流总览

```text
Phase 1 识别输入与定位文件
Phase 2 检查原始逻辑图
Phase 3 自动完善并二次检查逻辑图
Phase 4 转换逻辑图格式
Phase 5 调用 unicli 生成关卡
Phase 6 输出执行报告
```

每个 Phase 设有明确的**通过条件**和**阻断条件**。阻断时立即停止当前关卡、记录失败阶段和原因，跳至 Phase 6 生成部分报告。

## Phase 1 识别输入与定位文件

### 1.1 提取关卡 ID

从用户输入中提取一个或多个数字作为 `LevelId`。

示例：

| 用户输入 | LevelId |
| --- | --- |
| 制作脑洞关卡16 | `16` |
| 制作关卡16 | `16` |
| 制作关卡16,17 | `16`, `17` |

如果无法提取 `LevelId`，停止并要求用户补充关卡 ID。

### 1.2 定位原始策划案

按以下优先级查找原始文件：

1. `BrainGameLevel/关卡<LevelId>.md`
2. `BrainGameLevel/Level<LevelId>.md`
3. `BrainGameLevel/<LevelId>.md`

找到多个候选文件时，不自动选择，报告候选列表并等待用户确认。

找不到文件时，停止当前关卡并报告：

- 目标 `LevelId`
- 已搜索目录
- 期望文件名



## Phase 2 检查原始逻辑图

### 2.1 读取检查规则

读取以下文件：

- `$SKILL_ROOT/references/LogicTableGrammar.md`
- `$SKILL_ROOT/references/LevelError.md`

### 2.2 检查项目

逐项检查（按优先级排列，阻断项优先）：

1. 是否存在根节点 `Level<LevelId>`，且 LevelId 与当前关卡一致。
2. 是否存在 `游戏胜利` 指令。
3. 操作分支层级是否符合语法规则（参考 LogicTableGrammar.md 分支说明）。
4. 特殊分支层级是否符合语法规则（特殊分支下一层直接是指令层）。
5. 操作类型是否为以下之一：点击、双击、上滑、下滑、左滑、右滑、拖动类结构。
6. 物品名和动效名是否存在于物品表中（即逻辑图中出现的引用名称）。
7. 操作分支最后一个关键动效是否回到循环动效（如 `*_Idle`）或稳定状态。
8. if/else if/else 指令是否配对，是否缺少对应的 end 指令。
9. 是否包含无法识别的指令内容（参考 LevelLogicImprove.md 第2条）。
10. 操作分支是否存在重复的逻辑图内容（文件后半部分出现第二个根节点）。

### 2.3 错误处理规则

| 错误类型 | 严重程度 | 处理方式 |
| --- | --- | --- |
| 缺少原始文件 | 阻断 | 停止当前关卡 |
| 缺少根节点或 LevelId 错误 | 可修复 | 修改 LevelId 使之匹配，添加到报告 |
| 缺少 `游戏胜利` | 警告 | 添加到报告，不阻断 |
| 层级无法判断 | 阻断 | 停止当前关卡并报告 |
| 明显物品名或动效名缺失 | 警告 | 添加到报告 |
| if/end 不配对 | 可修复 | Phase 3 尝试修复，添加到报告 |
| 无法识别的指令 | 警告 | 移除并添加到报告 |
| 重复逻辑图内容 | 警告 | 取第一份，添加到报告 |

只有通过**阻断检查**后，才进入自动完善阶段。非阻断项记录到报告中继续执行。

**通过条件**：无阻断级错误。
**阻断条件**：存在层级无法判断或缺少根节点等阻断级错误。

## Phase 3 自动完善并二次检查逻辑图

### 3.1 读取完善规则

读取：

- `$SKILL_ROOT/references/LevelLogicImprove.md`
- 必要时重新参考 `$SKILL_ROOT/references/LogicTableGrammar.md`

### 3.2 自动完善规则

按以下顺序修改逻辑图，写入新文件，不覆盖原始策划案。

#### 3.2.1 特殊分支前置

如果存在被多个操作分支调用的特殊分支，例如：

- `完成所有线索`
- `完成条件1-8`
- `If条件1~8已完成`

则将该特殊分支放到操作分支之前，通常位于 `游戏开始` 之后。

判断特殊分支的识别规则：

1. 特殊分支名称中包含"完成所有"字样 → 所有操作分支需要调用。
2. 特殊分支名称中包含"完成条件X-Y"或"条件X~Y已完成" → 被条件 X 到 Y 标记的操作分支需要调用。

#### 3.2.2 完成条件补全

对于有"游戏胜利"或"游戏成功"指令的特殊分支，在指令层开头补全：

1. 若特殊分支是”完成所有线索“，则补充如下：

```text
- 设置 winLevel = <操作分支数>
- if playerLevel == winLevel
```

2.若特殊分支是需要完成指定条件的，例如`完成条件1-8`或者`If条件1~8已完成`，则补充判断所有指点条件是否完成，例如：

```base
if 条件1 == true &&条件2 == true &&条件3 == true &&条件4 == true &&条件5 == true &&条件6 == true &&条件7 == true &&条件8 == true
```



在指令层末尾补全：

```text
- 游戏胜利
- end
```

规则：

1. `<操作分支数>` 为该特殊分支被调用的次数（即依赖该特殊分支的操作分支数量）。
2. 保留原特殊分支内已有业务指令。
3. `游戏胜利` 前如存在语音指令且没有等待，可补充等待指令；等待时长不确定时使用保守值 `3s` 并在报告中说明。

#### 3.2.3 if 指令标准化

只在指令层识别 if 指令，将自然语言形式标准化为表达式形式：

| 原始写法 | 标准化写法 |
| --- | --- |
| if条件4完成 | `if 条件4 == true` |
| if条件2完成并且条件3未完成 | `if 条件2 == true && 条件3 == false` |
| if条件2未完成 | `if 条件2 == false` |
| if条件2完成或条件3未完成 | `if 条件2 == true || 条件3 == false` |

标准化规则：

1. "完成"/"已完成" → `== true`
2. "未完成"/"没完成" → `== false`
3. "并且"/"且" → `&&`
4. "或"/"或者" → `||`
5. 不修改已有标准格式的 if 指令。

#### 3.2.4 操作分支添加 `执行CheckGameOver`

如果有特殊分支中包含"游戏胜利"指令，则需要在每个操作分支的指令层开头添加：

```text
- 执行CheckGameOver
```

否则不添加。

#### 3.2.5 操作分支添加遮罩

凡是操作分支：

1. 在指令层开始添加 `显示InputMask`。
2. 在指令层末尾添加 `隐藏InputMask`。
3. 如果末尾需要调用完成条件特殊分支，则 `隐藏InputMask` 放在调用之后。
4. 如果操作分支中不包含等待指令，也需要添加 InputMask（统一规范）。

#### 3.2.6 操作对象交互后隐藏

凡是操作分支在指令层需要隐藏操作对象，例如是拖拽类型需要隐藏拖拽对象。在逻辑图对应操作分支中补充：

```text
- 隐藏<操作对象>
```

不补充的情况：

1. 当前指令已有 `隐藏<操作对象>`。
2. 当前指令已有 `<对象>升级成<高等级对象>`，升级语义已包含隐藏低等级对象。
3. 当前指令已有 `解锁<高等级对象>` 且有对应的 `隐藏<操作对象>`，需同时检查。
4. 操作对象是角色主体（如 `Boy_1`、`Girl_1`）、背景主体或持续交互对象，隐藏会改变策划意图。

不确定时不自动添加，写入报告中的待确认项。

#### 3.2.7 动效组转换

当连续出现同一物品类型的两个不同动效，且分别带有 `F`、`T` 标记时，转换为：

```text
- 动效组<T标记动效名>&<F标记动效名>&<序号>
```

规则：

1. `T` 标记动效放在第一位，表示多个 spine 播放。
2. `F` 标记动效放在第二位，表示单个 spine 播放。
3. `<序号>` 从 1 开始，按当前关卡中转换出现顺序递增。
4. 删除原动效指令下方单独的 `F` / `T` 标记行。
5. 如果两个动效不连续，或物品类型不同，不自动合并。
6. 对照示例验证：参考 `$SKILL_ROOT/references/example/test_fixed.md` 中动效组序号递增规律。

#### 3.2.8 操作分支调用完成条件

如果存在需要调用的特殊分支，则每个参与条件的操作分支在条件指令之后添加：

```text
- 执行<完成条件特殊分支名>
```

### 3.3 写入修复文件

输出到：

```text
BrainGameLevel/<LevelId>_fixed.md
```

如果存在 `OutputFile/` 子目录，则输出到：

```text
BrainGameLevel/OutputFile/<LevelId>_fixed.md
```

要求：

1. 不覆盖 `BrainGameLevel/` 中的原始文件。
2. 如果目标文件已存在，先生成带时间戳后缀的新文件（如 `<LevelId>_fixed_20260721_143000.md`），避免覆盖。
3. 保持 Markdown 层级缩进一致（每层缩进 2 个空格）。

### 3.4 增量二次检查

对 `_fixed.md` 执行增量检查，不重复 Phase 2 全部检查项，聚焦以下：

| 检查项 | 说明 |
| --- | --- |
| 修复文件存在且非空 | 文件写入成功 |
| 根节点 `Level<LevelId>` 保留 | 未被意外删除或修改 |
| `游戏胜利` 指令存在 | 胜利条件完整 |
| 特殊分支位于操作分支之前 | 前置规则生效 |
| 每个操作分支包含 `显示InputMask` 和 `隐藏InputMask` | 遮罩规则生效 |
| 每个操作分支包含 `执行CheckGameOver`（如适用） | CheckGameOver 规则生效 |
| 动效组序号连续递增且无遗漏 | 动效组合并规则生效 |
| if/end 配对完整 | 条件分支闭合 |
| 操作分支数量未减少 | 未丢失分支 |

二次检查不通过时：

1. 不执行转换脚本。
2. 不调用 `unicli`。
3. 报告失败原因和修复文件路径。

**通过条件**：增量检查全部通过。
**阻断条件**：任一项不通过。

## Phase 4 转换逻辑图格式

使用 `$SKILL_ROOT` 拼接脚本完整路径执行转换：

```powershell
powershell -ExecutionPolicy Bypass -File "$SKILL_ROOT/scripts/LevelTransform.ps1" -FileName "<fixedFileFullPath>"
```

说明：

- `<fixedFileFullPath>` 替换为 `_fixed.md` 的完整绝对路径。
- `$SKILL_ROOT` 替换为本 Skill 根目录的绝对路径。
- 不传入 `-BasePath`，因为当前脚本未声明该参数（脚本中 `$BasePath` 引用了未定义参数，输出目录默认为输入文件所在目录）。
- 默认输出为 `_fixed_output.md`，与 `_fixed.md` 同目录。

执行后检查：

1. 命令退出码是否为 0。
2. 输出文件是否存在。
3. 输出文件第一行是否包含 `- Level<LevelId>`。
4. 输出文件是否包含 `游戏胜利`。
5. 输出文件关键分支数量是否与修复文件一致（不应减少）。

任一检查失败，则停止当前关卡并报告。

可选：对照 `$SKILL_ROOT/references/example/test_fixed_output.md` 验证转换格式是否符合预期（`--` 开头表示第二层，`---` 开头表示第三层，依此类推）。

**通过条件**：转换成功且校验通过。
**阻断条件**：脚本执行失败或校验不通过。

## Phase 5 调用 `unicli` 生成关卡

unicli 命令超时设定为 60 秒。超时后记录失败原因并中止当前关卡的 Phase 5。

如果 unicli 命令未找到或不在 PATH 中，记录失败原因并中止，不重试。

### 5.1 初始化场景

执行：

```bash
unicli exec Level.InitializeGameLevel "{\"LevelId\":<LevelId>}" --json
```

成功条件：

1. 命令成功返回（退出码为 0）。
2. 未出现明确错误字段（如 `error`、`exception`、`failed`）。
3. 如约定生成 `<LevelId>_InitResult.json`，则文件存在且可读取。

初始化失败时，最多重试 1 次。第二次仍失败则不执行下一步，记录失败原因。

### 5.2 创建关卡逻辑块

初始化成功后执行：

```bash
unicli exec Level.CreateLevelLogicBlock "{\"LevelId\":<LevelId>}" --json
```

成功条件：

1. 命令成功返回。
2. 未出现明确错误字段。
3. 返回信息或生成文件能证明逻辑块创建完成。

创建失败时，最多重试 1 次。第二次仍失败则记录失败原因。

**通过条件**：初始化和创建均成功。
**阻断条件**：初始化或创建失败（含超时）。

## Phase 6 输出执行报告

读取 `$SKILL_ROOT/references/SkillExecutionReportTemplate.md` 获取报告模板，按模板格式生成报告。

报告必须包含：

1. `LevelId`。
2. 原始文件路径。
3. 修复文件路径。
4. 转换文件路径。
5. 原始检查结果。
6. 自动修复项列表。
7. 跳过或待确认项列表。
8. 二次检查结果。
9. 转换脚本执行结果。
10. `unicli` 初始化命令结果。
11. `unicli` 创建逻辑命令结果。
12. 失败阶段与失败原因，若有。
13. 读取并解析 `<LevelId>_InitResult.json`，按模板中的解析反馈文件部分以表格形式展示：
    - 解锁对象结果（inactiveResults）
    - 操作对象结果（operationResults）
    - 非操作对象挂载操作脚本结果（OrphanObjectInfo）
    - 错误隐藏操作对象结果（InactiveOperationItemResult）
14. 下一步建议。

如果 `<LevelId>_InitResult.json` 不存在或不可解析，在报告中标注"反馈文件缺失，跳过解析表格"，不阻断报告输出。

多关卡任务时，每个关卡生成独立报告节，最终汇总为一份完整报告，包含总体状态统计。

## 安全边界

1. 不覆盖原始策划案。
2. 不修改现有规则文档（`references/` 下的文件）。
3. 不修改现有脚本（`scripts/` 下的文件），除非用户明确要求。
4. 不能确定策划意图时，不自动改动，写入待确认项。
5. 多关卡任务中，一个关卡失败不影响其他关卡继续处理，但最终报告要分别说明。
6. 外部命令（unicli、powershell）超时应主动中止而非无限等待。
7. 文件写入前检查目标路径，存在时使用时间戳后缀避免覆盖。
